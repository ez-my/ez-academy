# Autosave persistence v2 — local architecture and verification

Status: implemented locally; independent release review still required. No deployment.

## Storage protocol

`PracticeAttempt` no longer rewrites one mount-owned object at `ez-progress-v1:<uid>:<skill>`.

- Account and skill have an isolated `ez-progress-v2:<encoded uid>:<skill>:` namespace.
- `draft:<writer UUID>` is one mutable slot owned exclusively by that mount. Its ownership rank is `(Lamport epoch, writer UUID)`, chosen once at construction from the highest durable draft epoch. A causally later remount outranks an older mount; pagehide/unmount cannot acquire a later epoch. For truly simultaneous mounts with the same observed epoch, UUID ordering deterministically chooses the active branch regardless of flush order. Both branch texts remain stored. The older page displays a conflict warning after it writes.
- Result versions use independent `result:<version UUID>` keys, including stable completion IDs and immutable text/feedback snapshots. `ack:<version UUID>` acknowledges only that exact version. Result-status callbacks never rewrite the active draft.
- There is no shared mutable queue index. Tabs enumerate the namespace and reduce the union of result versions by attempt ID. Assessed versions outrank unscored versions; a logical sequence and version UUID break ties. The exact immutable `resultVersion` / `resultOrder` travels through `saveSession`; the Firestore transaction uses the same shared comparator, so neither stale unscored nor stale scored retries can demote a newer winner. Equal-rank pre-version cloud records precede versioned results. Repeated writes of the same version retain its payload. The original completion timestamp and once-only reward are preserved.
- The transaction returns the effective persisted session only after commit. A superseded incoming version is not acknowledged: its effective winning version is retained locally and acknowledged instead. If a legacy cloud winner suppresses an unscored version, that winner receives a stable `legacy-cloud-<encoded attempt ID>` identity at order zero in the same transaction; it does not borrow the incoming identity. Existing owner session-write rules permit this optional metadata without rule changes; monotonicity is enforced by the cooperating client transaction, not a security-rules constraint on old/malicious clients.
- Editing an unfinished shared draft forks its future completion ID before a competing writer can complete a different answer under that ID. Finishing before the draft debounce also forks an edited answer. Once a result exists, its snapshot/ID is fixed: a pending different answer must be synced first; intentionally completing a revised acknowledged answer creates a new ID.
- Each retry processes at most 20 latest pending snapshots, with at most two automatic passes per mounted hook. Additional work remains durable for explicit retry/remount. Retry never invokes an assessment or replays audio. Storage events refresh queue visibility and can consume one of those bounded passes; reconnect also retries.
- Every device mutation and cloud invocation checks the current authenticated UID. If authentication changes during a save already sent to the cloud, the request cannot be cancelled, but the old callback writes no local acknowledgement and returns false. Its durable pending snapshot is safe to retry after signing back in.

This avoids an IndexedDB/schema migration and asynchronous page hydration: the existing synchronous draft-initialization contract stays intact. Correctness comes from disjoint writer/result keys and deterministic reduction, **not** a localStorage compare-and-swap or an in-memory singleton. localStorage is not transactional; we do not claim otherwise.

## Compatibility and failure honesty

Valid v1 device data is read without deleting or overwriting its original slot. Legacy completion snapshots are copied into v2 before the first authorized v2 mutation, independently of the active draft. A corrupted v1 record does not mask valid v2 data. Malformed, cross-account/type or oversized v2 records are not replayed. Records are limited to 256,000 JSON characters; oversized legacy records remain untouched and trigger a warning rather than being silently represented as durable work. Record schema checks cover kind, ID/version/order/epoch, account/type, timestamp, transcript and score. Each v2 key must also bind its record kind and exact version (result/ack) or owner (draft). An acknowledgement requires an actual ack record with the matching version, not merely an occupied key. Invalid records remain untouched, warn that local storage is not fully durable, and cannot suppress retry of valid pending work. The existing recording scrubber is applied; progress still contains text/metadata, never raw audio.

Quota/access/serialization failures retain the in-memory version and display the existing device-storage warning. A failed cloud write is never a successful account save. An older pending result remains visible even while the current draft is incomplete.

## Explicit limits / release review

- Tests use deterministic React lifecycle/DOM adapters and synthetic cloud transactions, not two live authenticated browser tabs or deployed Firebase rules. No learner data, credentials, paid calls or account creation were used.
- The ledger deliberately does not garbage-collect snapshots/branches or evict unsynced work. Retry work is bounded, but retained device history can eventually reach browser quota; the UI warns and retains unsynced memory rather than claiming durability. Safe cross-tab compaction or a branch-selection UI is a separate change.
- A losing simultaneous-edit branch is retained on the device but not automatically merged into the active answer. The active branch follows the documented ownership ordering, not wall-clock guessing.
- A model request already running in an old page may finish and its result will be retained. The retry queue makes no model calls. This change does not introduce a cross-tab paid-model execution lease or claim recovery of model responses if the browser process is killed before receiving them.
- Existing large-chunk build warning remains. No entitlement/pricing/provider migration, commit, push or deployment is part of this task.
